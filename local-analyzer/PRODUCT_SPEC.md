# Pilot 0｜本地开放式能力洞察分析器规格

## 1. 目的

Pilot 0 不是验证一个预先设定的结论，也不是把群聊做成摘要。

它要回答的是：在一个明确授权、范围受限的真实协作记录中，能否**开放地发现**值得进一步验证的组织能力缺口，并把每个判断还原为当事人可核对的证据与行动问题。

```text
真实协作记录（仅本地）
        ↓
格式正规化与匿名化
        ↓
开放式候选发现
        ↓
证据聚合与反证检查
        ↓
能力缺口假设 / 证据不足
        ↓
人工核对与反馈
```

它是未来平台插件的 **Core 原型**：以后飞书、钉钉或企业微信只替换“消息如何进入”的 Adapter；发现逻辑、证据门槛、结果页和人工确认应继续复用。

## 2. Pilot 0 的最小边界

| 项目 | Pilot 0 的选择 |
|---|---|
| 分析对象 | 一个明确授权的项目群或工作群；一个有限时间窗 |
| 数据位置 | 只在本机指定目录中读取；不上传 GitHub，不默认发送至任何云端模型/API |
| 输出 | 私密本地结果页与人工验证表；不自动发群、不生成正式人事/采购动作 |
| 决策权 | 业务/技术/HR 相关负责人；分析器只给草案 |
| 成功标准 | 发现至少一个当事人认可、证据充分、比普通聊天摘要更有行动价值的判断；或诚实输出“证据不足” |

Pilot 0 不应读取全公司聊天记录，也不应以绩效评估、员工监控、招聘淘汰或其他高影响个人决策为目的。

## 3. 一页检查清单（开始前）

### A. 范围与授权

- [ ] 试点群、时间窗与分析目的已由群主/负责方明确同意。
- [ ] 只使用完成该目的所必需的消息；不扩大到无关群聊。
- [ ] 原始文件保存在本机的私密目录，不进入仓库、网盘共享链接或截图材料。
- [ ] 已约定谁能看结果、保留多久、如何删除原始文件与结果文件。

### B. 开放探索任务

- [ ] 写下该群正在推进的业务目标或项目目标，而不是预设某一个能力缺口。
- [ ] 允许系统输出多个候选：能力供给、协同机制、资源配置、决策/信息接口，或“证据不足”。
- [ ] 不把抱怨、单次事故或某个人的表达直接当作组织结论。

### C. 结果与使用

- [ ] 结果只以“候选假设 + 证据 + 不确定性 + 待确认问题”呈现。
- [ ] 不根据结果自动联系员工、调整岗位、发起招聘、采购或发群公告。
- [ ] 结果页不默认导出完整原文；仅展示最小必要的、匿名化证据片段。

### D. 人工验证

- [ ] 至少两位熟悉现场、角色不同的人参与核对。
- [ ] 他们分别回答：看准了吗？证据够吗？遗漏了什么？建议能行动吗？
- [ ] 记录“误判/无效/证据不足”也是成功数据，不为证明产品而强行给出结论。

## 4. 输入策略：JSON 优先，Markdown 兼容

### 4.1 为什么 JSON 是主输入

JSON 通常能保留时间、发言顺序、发言人和群组等结构信息。这些信息是判断“是否反复出现”“是否跨角色”“是否跨任务”的基础。

Markdown 适合作为人工阅读和快速导入格式，但若缺少时间、发言人或顺序，结果的证据强度会下降。它可以被导入，但结果页必须标明可用元数据的缺失情况。

无论来自哪里，Adapter 都应把记录正规化为同一种内部结构；Core 不应直接依赖微信、飞书或 Markdown 的原始格式。

```ts
type CanonicalConversation = {
  schemaVersion: 'pilot-0.1';
  source: 'wechat_json' | 'markdown' | 'feishu' | 'manual';
  conversation: {
    id: string;              // 本地生成的匿名 ID，例如 pilot-group-01
    label?: string;          // 可选、匿名化的项目代号
    timeZone: string;
  };
  messages: CanonicalMessage[];
};

type CanonicalMessage = {
  id: string;
  sentAt?: string;           // Markdown 缺失时允许为空，但须标记
  sequence: number;          // 导入后稳定排序
  author: {
    alias: string;           // 例如 role-product-01，不保留真实姓名
    roleHint?: 'business' | 'product' | 'engineering' | 'hr' | 'operations' | 'unknown';
  };
  text: string;
  threadHint?: string;
  metadataCompleteness: 'full' | 'partial';
};
```

### 4.2 Adapter 责任

| Adapter | 输入 | 责任 | 不负责 |
|---|---|---|---|
| `WeChatJsonAdapter` | 原始 JSON 导出 | 字段映射、排序、去除媒体/附件、匿名化预览 | 推断组织结论 |
| `MarkdownAdapter` | 结构化 Markdown/纯文本 | 识别日期、发言人、消息边界；标明缺失元数据 | 虚构不存在的时间/角色 |
| 未来 `FeishuAdapter` | 经授权的飞书消息事件 | 将平台消息正规化为同一结构 | 绕过平台权限或读取未授权消息 |

第一版不需要把原始微信格式交给任何外部服务。若要实现精确 JSON 映射，只需日后查看**字段名与层级的脱敏样例**，无需提交真实消息内容。

## 5. 开放发现逻辑

### 5.1 先找“协作摩擦”，再形成“能力缺口候选”

分析器应从下列通用信号类别中开放检索，而不是从一个预设职位或技能词开始：

- 业务目标、承诺、时间/质量/成本约束；
- 反复阻塞、返工、等待、延期、失败和风险；
- 资源冲突、借人失败、单点依赖、职责不清；
- 跨角色或跨项目的接口断裂；
- 能力不足、学习/培养需求、外部依赖；
- 已尝试但效果不佳的解决办法。

之后按共同的业务结果、工作对象和协作关系聚类，形成候选假设。例如：

```text
候选假设，不是最终结论：
“多个任务都在结构—电子—软件交接处返工；可能存在跨域系统集成能力与接口治理不足。”
```

### 5.2 不让开放探索变成自由联想

每个候选假设必须经过以下检查。任何一项不满足，都只能保留为“观察”或“证据不足”。

| 检查 | 最低要求 |
|---|---|
| 重复性 | 至少 3 条独立消息，或在 2 个不同工作时点出现 |
| 证据多样性 | 至少跨 2 位发言人、2 个角色或 2 个工作对象之一 |
| 业务关联 | 能说明它怎样影响一个已出现的目标、交付、成本、风险或体验 |
| 反证检查 | 主动搜索“已解决”“仅偶发”“个人误会”“资源已可用”等相反证据 |
| 可解释性 | 每个判断可回到最小必要的原始片段；不得只给抽象评分 |

```ts
type CandidateStatus =
  | 'observation'            // 仅一两条信号
  | 'hypothesis_needs_review'// 有模式，但仍需人解释情境
  | 'action_ready_candidate' // 证据门槛已满足，值得讨论行动组合
  | 'insufficient_evidence';
```

### 5.3 候选的开放分类

Core 不应要求每个问题都落入“招聘”。它可暂时分类为：

```ts
type GapLens =
  | 'capability_supply'
  | 'operating_mechanism'
  | 'resource_allocation'
  | 'decision_or_information_interface'
  | 'local_delivery_issue'
  | 'insufficient_evidence';
```

一个候选可同时带多个 Lens。例如，缺少 Integration Owner 可能同时涉及人才供给、培养机制和跨专业决策接口。

## 6. 输出契约：先呈现判断，再呈现行动

每一个 `action_ready_candidate` 的结果页必须包含：

1. **观察到什么**：中性、可被现场人员确认的描述。
2. **候选能力/机制缺口**：用能力结果或协作机制表达，不直接用职位名替代。
3. **证据链**：匿名化片段、时间/角色分布、反证或不确定性。
4. **为什么可能是系统性问题**：重复、跨边界和业务影响的说明；若不是，明确标为局部问题。
5. **待确认问题**：分析器不知道、必须问人的情境。
6. **行动组合草案**：Recruit / Internal Mobility / Train / External Flexible / AI Enablement 的适用性与限制；没有足够证据时不排序行动。
7. **人工确认区**：`看准`、`部分看准`、`误判`、`证据不足`，以及备注字段。

结果页不应显示“员工排名”“个人能力评分”“谁拖后腿”等内容。

## 7. 本地运行与数据边界

Pilot 0 的默认模式是 **本地文件 → 本地浏览器结果页**。原始记录不得写入：

- Git 仓库与 GitHub Pages；
- 日志、错误追踪或分析统计服务；
- 浏览器 LocalStorage/云同步目录；
- 未经明确批准的外部模型 API。

如果未来使用外部模型进行语义提取，必须另行获得数据控制方的明确批准，并在界面上提示：哪些文本会发送到哪个服务、保留多久、能否关闭。Pilot 0 默认不走这条路径。

仓库根目录的 `.gitignore` 应忽略 `pilot-data/`、`pilot-output/` 和常见原始聊天导出命名，防止误提交。

## 8. 人工验证表

每位审核人对每个候选项独立填写：

| 问题 | 选项 |
|---|---|
| 对现场的描述准确吗？ | 看准 / 部分看准 / 误判 / 不确定 |
| 证据足以支持这个判断吗？ | 足够 / 还需补充 / 不足 |
| 这是局部问题还是系统性问题？ | 局部 / 系统性 / 暂无法判断 |
| 最有价值的行动方向是什么？ | 稳定拥有 / 内部发展 / 灵活调用 / AI 辅助 / 先不行动 |
| 系统遗漏了什么情境或反证？ | 自由文本 |

Pilot 0 的价值不以“找到多少缺口”衡量，而以是否减少误判、是否让现场人员提出更好的问题、是否帮助他们区分“局部修补”和“系统重塑”衡量。

## 9. 开发顺序

1. 建立 `CanonicalConversation` 与完全虚构的测试数据。
2. 开发 JSON/Markdown 导入预览：显示消息数、时间窗、缺失字段、匿名化映射；用户确认后才分析。
3. 开发开放式候选发现器与证据门槛检查器。
4. 开发私密结果页与人工验证表；默认不保存原始消息。
5. 使用一个明确授权、已匿名化的群聊做 Pilot 0；记录审核结果与误判。
6. 只有连续多轮验证表明价值成立，才评估飞书的主动触发或只读群观察接入。

## 10. Pilot 0 的退出条件

下列任一情况出现，应停止扩展数据范围，先改进 Core：

- 审核人普遍认为结果只是聊天摘要；
- 候选缺口无法回到可核对证据；
- 系统经常把单次事故、人际冲突或情绪表达误判为组织问题；
- 对行动建议没有新增价值，或引发不必要的个人归因；
- 授权、数据保留或结果可见范围无法说清。

反过来，只有在至少数轮试点中，结果被不同角色认为准确、可解释且有行动价值，才进入最小平台接入：用户主动触发、最小上下文、只读建议草案。
