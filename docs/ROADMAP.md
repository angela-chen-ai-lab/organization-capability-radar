# Roadmap

## v0.1｜证明机制（当前）

单一虚构项目群、规则引擎、能力缺口与行动组合、招聘能力画像、公开部署的互动 Web Demo。发布 GitHub 仓库，邀请共创者贡献场景、规则与界面。

## v0.2｜验证更多情境

增加 2–3 个行业/能力场景；可调整阈值；显示决策对比；收集访客反馈。

## 适配形态开发顺序｜同一个 Core，三个入口

先后顺序不是三套独立产品的优先级，而是用最低接入成本持续验证同一个 Core：

1. **Agent Skill**：用户导出、脱敏并主动提供材料；Skill 在已有 Agent 内执行 Core，输出证据与行动组合。最适合先开放共创和测试规则。
2. **本地应用（BYOK）**：保留浏览器导入与脱敏；由有能力的用户自行配置模型 API。适合受控试点，不要求我们托管模型费用。
3. **飞书/钉钉/企业微信插件**：在明确授权、最小上下文和人工触发前提下接入群聊。最后开发，因为它增加了平台权限、数据治理和持续运行的复杂度。

三种形态必须共用同一份输入/输出契约、Core 规则、证据门槛与人工确认边界；不能为某一平台重新发明诊断逻辑。

## v0.3｜受控真实数据试点

与一家愿意共创的团队开展有限、明确授权的飞书试点。先以单个批准群的只读接入或用户主动转发为起点；引入脱敏、审批、审计与数据保留策略；不直接接触候选人决策。

## v1.0｜平台化

飞书 Adapter、组织能力本体、内部流动/学习/供应商/ATS adapters、权限与治理、人工复核工作台。

## 邻接探索｜Capability Growth Studio（独立验证，不并入 Radar v0.1）

当 Radar 的建议指向内部培养时，用户自然会追问：具体培养谁、怎么培养、用哪些真实任务、是否需要知识库或 AI 工作辅助？这是一条重要但独立的产品方向。

先验证其问题与适用条件，再决定是否立项：组织规模与项目节奏、现有知识资产、导师可用性、任务风险，以及碎片化学习、集中训练和 learning by doing 的选择逻辑。Radar 只输出交接 Brief，不承担完整培养体系的设计与运行。

## 开源协作原则

先把规则、场景和解释性做好，再增加模型与集成。每项连接真实组织数据的能力必须独立设计隐私、安全与授权边界。
