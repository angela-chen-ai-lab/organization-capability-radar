# 共创贡献归因与未来价值原则

## 为什么要先写这件事

这是一个希望通过公开讨论、案例、规则、设计与代码共同演进的项目。贡献不只来自代码：一个指出误判边界的真实案例、一套更好的规则、一次试点反馈，可能比一段实现代码更影响产品方向。

因此，项目应当记录贡献、给予可见署名，并在未来出现商业价值时拥有可讨论的共同依据；但也不能在尚无主体、收入、预算或商业模式时，轻率承诺固定分成或股权。

## 当前阶段：开源共创，不自动产生经济权利

目前是探索与验证阶段。任何 Issue、评论、案例、文档、设计或 Pull Request 都会进入公开协作记录；贡献者保留其署名，项目可在仓库许可范围内使用被合并的贡献。

**提交贡献本身不自动产生工资、收益分成、股权、雇佣关系或代理关系。** 若未来产生商业合作、付费试点、产品收入或实体公司，应在对应事项开始前，以单独书面协议约定权利、义务、保密、知识产权与报酬。

这不是回避分配，而是避免在贡献尚未可衡量、商业价值尚未发生时做出无法兑现的空泛承诺。

## 我们承诺的四件事

1. **可追溯**：有实质影响的贡献应通过 Issue、PR、讨论纪要或贡献记录保留来源与时间。
2. **可见署名**：被合并的代码、规则、案例框架、设计或研究结论，应在提交记录、Release Notes、案例/规则文档或 Contributors 页面中按适当方式致谢。
3. **贡献不只看代码**：研究、业务验证、反例、数据治理建议、设计、测试、社区组织与技术实现都可被记录。
4. **商业合作另行谈判**：当某项贡献直接进入付费客户项目、商业产品或新实体时，发起方应在使用前与相关贡献者讨论适当的合作形式，而不是事后默认占有。

## 贡献记录：看影响，不做机械积分

本项目不采用“提交次数 = 贡献价值”的机械积分。每项被采纳的重大贡献可记录以下信息：

| 字段 | 说明 |
|---|---|
| 贡献者 | GitHub 用户名或贡献者希望使用的公开署名 |
| 贡献类型 | 场景/研究、规则、设计、代码、测试、试点、社区等 |
| 解决了什么 | 对应问题、误判、体验摩擦或能力缺口 |
| 证据 | Issue、PR、讨论链接或版本号 |
| 影响范围 | 影响一个案例、一个规则、一个功能，还是产品方向 |
| 采纳状态 | 提出 / 试验中 / 已采纳 / 未采纳及原因 |

### 贡献层级仅用于致谢与合作讨论

- **参与贡献**：提出问题、反馈体验、补充小型文档或案例。
- **实质贡献**：被采纳的规则、案例、设计、代码、测试或试点洞察。
- **方向性贡献**：显著改变 Core、产品边界、关键能力模型或商业/治理路径的贡献。

层级不是职级，不用于给人排名；它只帮助项目在发布致谢、邀请试点、组建工作小组或讨论未来合作时，避免遗漏真正推动项目的人。

## 如果未来产生收入，怎样讨论才公平

未来的价值分配不应按今天的模糊承诺预先切蛋糕，而应针对具体机会逐项讨论。至少应考察：

- 贡献是否直接进入该客户项目、付费产品或新实体；
- 是否持续投入交付、维护、客户支持或风险承担；
- 贡献是否可替代、是否形成核心 IP/规则/技术；
- 使用的是公开开源成果，还是额外的私有工作成果；
- 机会发生时各方投入的时间、资金、责任与机会成本。

可选合作形式包括：按项目付费、顾问合作、维护资助、收益分成、联合研发协议或在设立实体后讨论股权。具体形式必须另行书面确认，不能由本文件自动触发。

## 仍待共创的问题

1. 是否需要公开的 `CONTRIBUTORS.md`，记录被采纳的实质贡献？
2. 何种案例或田野反馈应被视为“方向性贡献”？
3. 在开放案例与保护企业/个人隐私之间，如何给予研究贡献者可见署名？
4. 开源 Core 与未来私有 Adapter、试点服务或商业交付，应如何保持清晰边界？

## 重要提示

本文件是项目治理与沟通原则，不是法律意见、合伙协议、劳动合同或收益分配协议。涉及收入、股权、专有数据、客户项目或长期合作时，应先由相关方形成明确书面约定并在需要时咨询专业人士。
